# Stage Prompts

Per-stage prompt templates referenced by `scene`/`video-manifest` records.
These consolidate constants that previously lived inside individual,
now-archived scene scripts (e.g. `video2_scenes.py`'s `SAFETY_SUFFIX`,
`CHARACTER_ANCHOR`) plus the validated-but-unwired `COLOR_ANCHOR` from the
Phase 2 A/B test, so the next scene file pulls from one documented place.

## 1. Script generation (LLM: Groq primary, TokenRouter fallback)

```
prompt_id: stage-script-v1
```

Input: a `story-input` record. Output: narration text broken into scenes,
English only, following `prompts/CORE-CREATIVE-PROMPT.md`'s brief and
content rules. Must not estimate scene screen-time in the output — screen
time is derived later from measured audio (`TECHNICAL-SPEC-EN.md` §7), not
generated by the LLM.

## 2. Scene image prompt construction (Qwen-Image)

```
prompt_id: stage-scene-image-v1
```

Every scene image prompt sent to `image_qwen.generate_with_reference()`
must append, in this order, after the scene-specific visual description:

1. **`CHARACTER_ANCHOR`** — the canonical character description pulled from
   the active `role-outfit` record (proportions, palette, default outfit).
   Required whenever the character appears in the scene; without it,
   plain generation drifts on head shape/proportions/shading scene to
   scene (`CLAUDE.md`).
2. **`COLOR_ANCHOR`** (validated Phase 2, A/B tested):
   ```
   Consistent warm color grading across the whole scene: soft golden-amber
   lighting, gentle warm shadows, calm and emotionally intimate mood,
   cohesive muted color palette — avoid harsh contrast or clashing
   saturated colors.
   ```
   Tradeoff (documented in `CLAUDE.md`): flattens dramatic contrast
   somewhat. For a scene that specifically wants tension or gloom, this
   wording should be revisited rather than silently dropped — dropping it
   reintroduces the scene-to-scene palette drift it was added to fix.
3. **`SAFETY_SUFFIX`** — negates pencil crosshatch shading and black
   backgrounds (both confirmed to leak into outputs from underspecified
   prompts per `CLAUDE.md`'s video1 style-bug note), and reiterates "no
   text/numbers" (understanding that instruction alone is not fully
   reliable — see visual spot-check rule below).

Every generated image for a scene containing text-adjacent objects
(screens, gauges, dials, signage) must be visually spot-checked before use;
"no text" in the prompt is necessary but not sufficient
(`TECHNICAL-SPEC-EN.md` §4, `CLAUDE.md` known-bugs list).

## 3. TTS preparation (Kokoro)

```
prompt_id: stage-tts-prep-v1
```

Not an LLM prompt — a text-normalization pass before synthesis: strip any
markup/formatting from the script, keep narration English, do not insert
estimated pause/timing markers meant to predict duration (duration is
measured after synthesis, never predicted before it).

## 4. Text overlay generation (deterministic, no LLM call)

```
prompt_id: stage-overlay-v1
```

Overlay text is derived directly from the scene's narration text and
measured timing via a fixed template (e.g. a short pull-quote or keyword
extracted by a fixed rule, not a fresh LLM generation per render) — see
`TECHNICAL-SPEC-EN.md` §8. This keeps `visual.deterministic_text_overlays_enabled`
true: the same manifest always yields the same overlay text and timing.

## 5. Manual Flow handoff note (human-readable, not a generation prompt)

```
prompt_id: stage-manual-flow-note-v1
```

When a `manual-flow-task` is created, its human-readable instructions
should state plainly: (a) this step is optional, (b) the video already has
a complete, publishable local render without it, (c) what specific clip
would benefit and why. Never phrase it as a blocking requirement.
